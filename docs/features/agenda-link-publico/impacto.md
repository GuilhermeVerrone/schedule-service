# Impacto: Agenda e link público

| Camada | Afetada? | O quê | Risco |
|--------|----------|-------|-------|
| Infraestrutura | pouco | Nenhum serviço novo. `btree_gist` já existe (migração init, usada em working_hours). Nova migração Prisma + SQL manual (exclusion constraint). Env sem novidade | Migração em dev e test; constraint não é expressa pelo Prisma e precisa de teste que a contorne |
| Arquitetura | sim | `tenant-repository.ts` (9,9K) ganha Customer, Appointment, TimeBlock e settings: separar em módulos por domínio. Novo módulo de cálculo de horários livres (função pura, fuso do tenant). Novo repositório público resolvendo tenant por slug (hoje todo acesso exige tenantId da sessão). `proxy.ts` hoje trata toda `/api` como protegida, salvo 3 rotas: precisa de prefixo público (ex.: `/api/public/{slug}/...`). `check-tenant-access.ts` lê modelos do schema, então cobre as novas tabelas sozinho | Repositório público é a única brecha de leitura sem sessão: deve expor só campos públicos e nunca aceitar tenantId do cliente. Rota `/{slug}` disputa o namespace raiz com `/login`, `/cadastro`, `/painel`, `/api` e assets |
| Visual | sim | Site público: layout próprio com menu (Início, Serviços, Equipe, Agendar em passos), mobile-first. Painel: `/painel/agenda` (dia/semana, lista no celular), `/painel/configuracoes`, item novo no menu do painel. Estados vazio/carregando/erro; página 404 por slug | Maior fase de UI do projeto; calendário no celular; fidelidade ao DESIGN.md da Algoritmi; negócio sem serviços/profissionais ativos precisa de estado vazio no site |
| Dados | sim | Tabelas `customers`, `appointments`, `time_blocks`; colunas novas em `tenants` (descrição, endereço, telefone, 5 parâmetros da agenda com padrões e CHECKs). FKs compostas (tenant_id, id) como na Fatia 1. EXCLUDE gist em appointments (profissional + intervalo, só `confirmed`); índices por (tenant, profissional, início). Slugs reservados: tenants existentes ou novos com slug reservado (ex.: nome "Login" gera `login`) | Tenant já cadastrado com slug reservado quebraria a rota (migração precisa renomear e o cadastro passar a validar). Agendamento com serviço/profissional arquivado depois: histórico deve sobreviver (arquivar, não apagar). Remarcar = atualizar ou cancelar+criar, sob a mesma constraint. Buffer entra no bloqueio do horário ou só na grade: definir no plano |
| LGPD | sim | Nome e telefone de terceiros (clientes finais) sem conta. Consentimento no formulário; token de gestão só em hash; sem exclusão automática | Telefone é dado pessoal exposto a quem tiver o link de gestão: a página do token mostra só o necessário. Direito de exclusão do cliente fica como pendência registrada (já havia nota de exclusão de conta) |
| Performance | pouco | Cálculo de horários por profissional e dia lido por intervalo (índice tenant+profissional+início); janela de 60 dias com passo de 15 min = poucas centenas de slots por dia/profissional. Painel lê por intervalo | "Qualquer profissional" multiplica a consulta pelo nº de profissionais; carregar a semana inteira de uma vez no site é desnecessário, buscar por dia |
| Segurança | sim | Primeira superfície pública que escreve dados. Limite de requisições por IP (hoje a tabela `login_attempts` é específica de login: generalizar ou criar tabela própria). Token de gestão aleatório com hash SHA-256 (padrão da sessão). Corrida: duas gravações simultâneas resolvidas pela constraint (409). Validação Zod em todas as entradas públicas. Isolamento: slug de um tenant nunca devolve dado de outro | Enumeração de horários/clientes por rota pública (não expor dados de clientes na disponibilidade); spam de agendamentos falsos (mitigado só por limite de IP, sem verificação de contato: risco aceito, decisão 5); token vazado no histórico/Referer (usar cabeçalho de política de referência) |

## Riscos que viram fase ou item de fase
- Slug reservado e migração de tenants existentes -> fase de schema/migração e cadastro (validar slug)
- Constraint de sobreposição + teste que a contorna -> fase de schema
- Separar o repositório por domínio e criar o repositório público por slug -> fase de repositório
- Prefixo de API pública no proxy e limite de requisições -> fase de API pública
- Cálculo de horários (fuso, virada de dia, bloqueio, buffer) como função pura testada -> fase própria antes das rotas
- Token de gestão sem vazamento (Referer, hash) -> fase de cancelar/remarcar
- Histórico com serviço/profissional arquivado -> fase de schema
- Maior volume visual (site + painel + configurações) -> separar em fases de tela
- Exclusão de dados do cliente (LGPD) -> pendência registrada fora desta fatia
